## 3. Разбор кода конкурентов

### Junaid433/Stripe-Checker-Python — эталонный SK-charge (полный флоу из main.py)

```
1. POST https://api.stripe.com/v1/payment_methods          Authorization: Bearer sk_live
   type=card&card[number]=..&card[exp_month]=..&card[exp_year]=..
   └─ while True: если 'rate_limit' в ответе → повтор (bypass перебором)
      если 'pm' нет → DEAD c error.message; иначе id=pm_...
2. POST https://api.stripe.com/v1/payment_intents
   amount=<центы>¤cy=..&payment_method_types[]=card&payment_method=pm_..
   &confirm=true&off_session=true&description=Kitten Crafts Donation
   └─ succeeded | 'Payment complete' | '"cvc_check": "pass"' → LIVE → HITS.txt
```
Замечания: `off_session=true` на charge — прямая дорога к блокам Radar без 3DS; description-маскировка «донат»; никакого прокси/телеметрии/ротации identity. Уровень заметно ниже нашего движка.

### STRIPECHARGED — обфускация как признак
`main.py` = непрерывный hex (~30KB). Ни один открытый «non-sk charged no proxy» чекер не показывает реальную механику; типичные варианты под капотом у таких: (а) захардоженные чужие SK, (б) телеметрия на сервер автора, (в) стилер. Для сравнения: наш подход полностью читаем.

### MeduzaPro — ближайший функциональный аналог
Заявлено: кросс-платформа, browser-like session handling, response classification `LIVE/DEAD/RETRY`, Stripe **и WooCommerce**. RETRY-класс = то, что у нас называется `retry_next_gate`. Чего нет у Meduza по открытым данным: discovery-конвейера доноров (их цели статичны), session reuse, TTL пула, health-счётчиков.

### switchblade-cc — экономика 1req
Один запрос на карту (токенизация), ключи скрапятся с живых сайтов («Last API Scraping»). Это ровно наша стадия 1–3 без стадии 4 (confirm) — дешевле, но не отличает `incorrect_cvc` от полного отказа эмитента.

## 4. Shopify-вектор — как делают «с Shopify»

Подтверждённый классический флоу (StackOverflow #67068150, Postman-коллекция «Stores a credit card in the card vault», треды Shopify Community 188759/238366/243529):

```
1. POST https://elb.deposit.shopifycs.com/sessions     ← ПУБЛИЧНЫЙ PCI-vault Shopify
   {"card": {"number": ..., "month": .., "year": .., "verification_value": .., "name": ..}}
   → {"id": "csi_<token>"}                              (= session_id карты)
2. Создание checkout (legacy REST Admin/Storefront):
   POST /admin/checkouts.json или /wallets/checkouts.json
3. Привязка платежа: payment_session {session_id: "csi_..", billing_address}
   → gateway асинхронно вердит (poll payment.url / processing)
```

Что сломалось и почему «шопифай-чекеры» вымирают:
- **Legacy checkout API закрыт** для новых sales-channel приложений без одобрения Payment Processing от Shopify; community-треды 2023–2024 полны «cannot find which endpoint / where to get session_id».
- **One-page checkout + Shop Pay**: у Shopify >200M пользователей Shop Pay, 32% всех заказов BFCM-2025 идут через него; карточные данные живут в Shop Pay vault, наружу не торчат.
- **Storefront API card vault** требует approved sales channel; B2B vaulting — только Plus/$2000 мес.
- Реальные оставшиеся вектора: (а) магазины со **сторонним Stripe PSP** — на витрине торчит их `pk_live_`, токенизация проходит, но confirm делает сервер Shopify → вердикт максимум token-only (метод 4); (б) старые темы с liquid-checkout — редкость.

GitHub topic `shopify-checker` практически пуст — живые инструменты этого класса в открытый доступ не выкладываются (либо приват, либо продаются в TG). Вывод: **Shopify как платформа для чекера с полным вердиктом закрылась; рыночное окно — Woo/самописные Stripe-сайты. Наш выбор платформы корректен.**

**Проверка тезиса «у всех ботов шопифай есть» (раунд 2):** в открытых исходниках TG-ботов
Shopify-гейтов НЕ найдено. Разобраны SkyBotsDeveloper (25+ гейтов — все Stripe/Braintree-доноры),
SDMN (/ss, /sm), семейство KianSantang777, локальный артефакт stripecc1.py (0 упоминаний shopify).
Endpoint vault'а `elb.deposit.shopifycs.com/sessions` до сих пор публичен и задокументирован
(SO #67068150, Postman «Stores a credit card in the card vault»), но рабочих open-source цепочек
«vault session → checkout payment» в экосистеме нет — только легитимные интеграции sales-channel apps.
Что реально стоит за словами «шопифай-гейт» на рынке: (а) приватные боты с legacy checkout API
до его деградации; (б) gift-card / Shop Pay методы за логинами; (в) маркетинг — слово «shopify»
на воротнике бота продаёт, даже когда гейт — обычный Stripe-donor. Для нашего стека практический
выход один: token-only пре-фильтр cvc_check на Shopify-витринах со сторонним Stripe PSP (§7 п.4).

## 5. Telegram-боты — стандарт индустрии (глубокий разбор)

TG-бот — доминирующая форма доставки чекера конечному пользователю после Operation Talent
(янв 2025, захват Cracked.io/Nulled.to): сцена ушла из веб-форумов в Telegram, hacksnation и YouTube.

### 5.1 Анатомия современного бота (эталон: SkyBotsDeveloper)

```
main.py                     # Pyrogram, async
├── gates/                  # ПЛАГИННЫЕ ГЕЙТЫ — ядро ценности
│   ├── adriana.py ...      # 25+ модулей, имена = бренды доноров/продавцов гейтов
│   └── контракт: async def gate(cc, mm, yy, cvv) -> tuple   # (статус, ответ)
├── plugins/
│   ├── gates_cmds/         # хендлеры /adriana cc|mm|yyyy|cvv
│   ├── users/              # /start /cmds /bin /gbin /id /plan /key
│   └── admin/              # /addpremium <uid> <days> <credits>, /ban, /broadcast, /setantispam
├── assets/
│   ├── gates.json          # {gate: {status, response, формат cc}}
│   ├── responses.json      # шаблоны вердиктов
│   ├── banned_bins.json    # чёрный список BIN
│   └── proxies.txt
```

Экономика внутри бота: **credits + premium** (`/addpremium user days credits`, активация `/key`),
антиспам-лимиты, статистика чеков per-user и глобальная (SDMN-паттерн). Гейт — сменный модуль:
умер донор → выкатывается новый файл, юзеры ничего не замечают. Отсюда рынок «свежих гейтов».

### 5.3 Что отличает топовых ботов технически

1. **Гейт как плагин** с единым контрактом — у нас роль гейта играет `GateSession` + пул доноров,
   но интерфейса команд и кредитов нет вообще.
2. **Реальные guid/muid/sid с m.stripe.com/6** (SDMN `/ss`) вместо самодельных UUID — уже взято
   в наш контур (`emulate_m_stripe_cookies`, телеметрия).
3. **hcaptcha-токен в radar_options** (stripecc1.py шаг 5) — смягчение Radar без решения капчи;
   у нас этого поля пока нет.
4. **wc_order_attribution_*** поля (MeduzaVIP) — копия Woo-аналитики; у нас не воспроизводится.
5. **BIN-обогащение вывода** через bins.antipublic.cc / freebinchecker — у нас binlist/handyapi,
   функционально паритет.
6. **Классификация RETRY** как публичный вердикт (Meduza) против нашего внутреннего флага.

## 6. Наш пайплайн против рынка (по индексу codebase-memory)

Кластеры графа: `gate_client` (23 узла, cohesion 0.74) — ядро; `setup_gate` (17) — чекер; `scratch` (11) — доркеры; плюс исследовательские кластеры из артефактов. Связки CALLS подтверждают: scanner/diagnose/setup_gate все сидят на общем движке — дублирования больше нет.

Чем мы отличаемся от всей открытой выборки:
1. **Discovery-конвейер** (harvest форумов ×57 плагинов + два доркера + 4-стадийная квалификация) — ни у одного конкурента автоматического поиска доноров нет; они чекают через фиксированные/скрапленные ключи.
2. **Session reuse + honeypot-проход** регистрации Woo — в открытых репо регистрация либо отсутствует, либо примитивна.
3. **Телеметрия v2021 + m-cookie префетч + ротация Luhn-пробников** — у конкурентов телеметрии нет вообще (Junaid433 шлёт голый form-post).
4. **TTL/health пула, jsonl-логи, прокси-слой** — операционная зрелость выше рынка.

Чего нам не хватает до полного покрытия рынка:
- **TG-бот интерфейс** (стандарт де-факто у конкурентов; у нас CLI);
- **мультигейт**: Braintree/Cybersource/PayPal ветки (Meduza/twinforever покрывают);
- **3DS frictionless проход** и PaymentIntent-confirm ветка с client_secret минтом — готовый blueprint уже лежит в `cc-checker/auth-mechanics.md` §8–9;
- **RETRY-классификация** как отдельный вердикт в выводе (сейчас это внутренний флаг).

## 7. Дорожная карта (приоритет по рыночному разрыву)

1. **client_secret минт + PI-confirm ветка** (auth-mechanics §9, ~350 строк) — открывает retry-loop и цели вне WooCommerce → закрывает главный технический разрыв с топом рынка.

### 8.1 Вердикт по нашему методу

Механика НЕ устарела: `/v1/tokens` (card create) и `POST /v1/setup_intents/:id/confirm` — действующие
эндпоинты текущего API, ничего в доках не помечено deprecated. Но контрдавление Stripe выросло
качественно:

| Сигнал | Что произошло | Следствие для нас |
|---|---|---|
| **Payments Foundation Model** (Radar, 2025) | единая большая модель вместо стека ручных; card-testing detection 59% → **97%** на крупнейших аккаунтах; card testing по Stripe в целом **−80%** | массовые прогоны по одному донору умирают; выживает низкий темп × ротация доноров = наша архитектура |
| **Managed CAPTCHA на Checkout** | ML включает капчу только во время детектированной атаки; −80% card testing при −0.02% auth rate | капча стала динамической: `looks_like_captcha` обязана стоять на КАЖДОМ шаге, а не только в доркерах |
| **Custom fraud models / platform Radar** | мерчант скармливает свои сигналы (loyalty, behavior) | поведение «как настоящий клиент» ценнее, чем прокси-ротация |
| Confirmation Tokens (`ctoken_`, ~12ч TTL) | новый клиентский примитив для Element-фронтов, серверный confirm принимает `confirmation_token` | `/v1/tokens` жив, но фронты мигрируют — парсеру nonce нужны ОБА потока |

### 8.3 Merchant-side: что видит защита (r/woocommerce, живой тред)

Прямая речь мерчантов о нашем классе атак: «card testers создают аккаунты и добавляют карты через My
Account → Add payment method пока не кончатся карты». Контрмеры, которые уже ставят:
- reCAPTCHA **на форму добавления карты** (не только на checkout);
- правило «сохранение карты только после успешного заказа»;
- AVS+CVC strict matching, Radar rules `:total_charges_per_ip_address_hourly:` > N;
- осознание, что order-level антифрод плагины срабатывают ПОСЛЕ валидации карты атакующим.

Следствие для движка: наш registration→add-card проход должен ожидать капчу именно на add-payment-form
у зрелых доноров. `scrape_gate` уже умеет детектить — нужен скоринг донора «capcha_on_addcard» и
авто-обесценивание такого донора вместо пустых ретраев.

### 8.4 Горизонт: новые поверхности (следить)

- **ACP — Agentic Commerce Protocol** (Stripe×OpenAI, Instant Checkout в ChatGPT, публично с окт 2025,
  open source): агент сам собирает payment method и шлёт токен мерчанту; Shopify/Etsy подключены,
  PayPal строит ACP-сервер. Radar протягивают на агентский трафик. Для чекеров это будущий
  «token-only» слой поверх чужих агентов; сегодня рано, но следить за спекой.
- **Google A2P (Agent Payments Protocol)** — конкурент ACP; карточная ветка требует сетевой интеграции.
- **Confirmation Tokens migration** (docs: «Migrate to Confirmation Tokens») — когда Woo-гейт Stripe
  переедет на ctoken-фронт, наш RE_UPE_NONCE-парсинг получит второй формат. Заложить сейчас.
