<h3 class="anchor anchorTargetStickyNavbar_i37j" id=switching-from-recaptcha>Switching from reCAPTCHA<a href=#switching-from-recaptcha class=hash-link aria-label="Direct link to Switching from reCAPTCHA" title="Direct link to Switching from reCAPTCHA" translate=no>​</a></h3>
<p>If you're already using Google's reCAPTCHA, you can use your existing code with <a class="" href=/switch>only a few changes</a>. <strong>hCaptcha</strong> methods are API-compatible with <strong>reCAPTCHA</strong> methods, for example <code>render()</code> and <code>onload()</code>. Custom data attributes like <code>theme</code>, <code>size</code>, and <code>tab-index</code> are also supported in the same way by hCaptcha.</p>

<ol start=2>
<li class="">The user starts an hCaptcha evaluation: they click the checkbox or submit button, or you trigger it programmatically.</li>
<li class="">The user gets a token from our server. This is embedded in your form or returned to your JS callback.</li>
<li class="">The user clicks Submit. The passcode is sent to your server in the form.</li>
<li class="">Your server sends the token to our API (<code>api.hcaptcha.com/siteverify</code>). hCaptcha says it is valid. Your server now knows the user is not a bot and lets them log in. Pretty simple!</li>
</ol>

<h2 class="anchor anchorTargetStickyNavbar_i37j" id=content-security-policy-settings>Content-Security-Policy Settings<a href=#content-security-policy-settings class=hash-link aria-label="Direct link to Content-Security-Policy Settings" title="Direct link to Content-Security-Policy Settings" translate=no>​</a></h2>
<p>Content Security Policy (CSP) headers are an added layer of security that help to mitigate certain types of attacks, including Cross Site Scripting (XSS), clickjacking, and data injection attacks.</p>
<p>If you use CSP headers, please add the following to your configuration:</p>
<ul>
<li class=""><code>script-src</code> should include <code>https://hcaptcha.com, https://*.hcaptcha.com</code></li>
<li class=""><code>frame-src</code> should include <code>https://hcaptcha.com, https://*.hcaptcha.com</code></li>
<li class=""><code>style-src</code> should include <code>https://hcaptcha.com, https://*.hcaptcha.com</code></li>
<li class=""><code>connect-src</code> should include <code>https://hcaptcha.com, https://*.hcaptcha.com</code></li>
</ul>
<p>Please do <strong>not</strong> hard-code specific subdomains, like <code>newassets.hcaptcha.com</code>, into your CSP: asset subdomains used may vary over time or by region.</p>
<p>If you are an enterprise customer and would like to enable additional verification to be performed, you can optionally choose the following CSP strategy:</p>
<ul>
<li class=""><code>unsafe-eval</code> and <code>unsafe-inline</code> should include <code>https://hcaptcha.com, https://*.hcaptcha.com</code></li>
</ul>
<h2 class="anchor anchorTargetStickyNavbar_i37j" id=add-the-hcaptcha-widget-to-your-webpage>Add the hCaptcha Widget to your Webpage<a href=#add-the-hcaptcha-widget-to-your-webpage class=hash-link aria-label="Direct link to Add the hCaptcha Widget to your Webpage" title="Direct link to Add the hCaptcha Widget to your Webpage" translate=no>​</a></h2>
<p>hCaptcha requires two small pieces of client side code to render a widget on an HTML page. First, you must include the hCaptcha javascript resource somewhere in your HTML page. The <code>&lt;script></code> must be loaded via HTTPS and can be placed anywhere on the page. Inside the <code>&lt;head></code> tag or immediately after the <code>.h-captcha</code> container are both fine.</p>

<h2 class="anchor anchorTargetStickyNavbar_i37j" id=verify-the-user-response-server-side>Verify the User Response Server Side<a href=#verify-the-user-response-server-side class=hash-link aria-label="Direct link to Verify the User Response Server Side" title="Direct link to Verify the User Response Server Side" translate=no>​</a></h2>
<p>By adding the client side code, you were able to render an hCaptcha widget that identified if users were real people or automated bots. When the challenge succeeded, the hCaptcha script inserted a unique token into your form data.</p>
<p>To verify that the token is indeed real and valid, you must now verify it at the API endpoint:</p>
<div class="language-text codeBlockContainer_OZUn theme-code-block" style=--prism-color:#393A34;--prism-background-color:#f6f8fa><div class=codeBlockContent_Prpx><pre tabindex=0 class="prism-code language-text codeBlock_mFd_ thin-scrollbar" style=color:#393A34;background-color:#f6f8fa><code class=codeBlockLines_aUJ3><span class=token-line style=color:#393A34><span class="token plain">https://api.hcaptcha.com/siteverify</span><br/></span></code></pre></div></div>
<p>The endpoint expects a POST request with two parameters: your account secret and the <code>h-captcha-response</code> token sent from your frontend HTML to your backend for verification. Do not send JSON data: the endpoint expects a standard URL-encoded form POST.</p>
<p>Additionally, you should include the user's IP address for enhanced security. While not strictly required, providing the IP address helps improve verification accuracy. For Enterprise customers, this also enables risk scores.</p>
<p>A simple test will look like this:</p>
<div class="language-bash codeBlockContainer_OZUn theme-code-block" style=--prism-color:#393A34;--prism-background-color:#f6f8fa><div class=codeBlockContent_Prpx><pre tabindex=0 class="prism-code language-bash codeBlock_mFd_ thin-scrollbar" style=color:#393A34;background-color:#f6f8fa><code class=codeBlockLines_aUJ3><span class=token-line style=color:#393A34><span class="token plain">curl https://api.hcaptcha.com/siteverify \</span><br/></span><span class=token-line style=color:#393A34><span class="token plain">  -X POST \</span><br/></span><span class=token-line style=color:#393A34><span class="token plain">  -d "secret=YOUR-SECRET&remoteip=CLIENT-IP&response=CLIENT-RESPONSE"</span><br/></span></code></pre></div></div>
<ul>
<li class=""><code>CLIENT-RESPONSE</code> is the token returned by the hCaptcha SDK to the client.</li>
<li class=""><code>YOUR-SECRET</code> is your sitekey secret ("ES_...") that you generated in the dashboard.</li>
<li class=""><code>CLIENT-IP</code> is the client's IP address. While <code>remoteip</code> is not strictly required, providing it helps improve verification accuracy.</li>
</ul>
<p>The endpoint expects the <code>application/x-www-form-urlencoded</code> Content-Type. Make sure the body is actually form-encoded, not just concatenated by hand: reserved characters must be percent-encoded, and spaces must be sent as <code>+</code> per form encoding rules. Most HTTP client libraries, such as Python <code>requests</code>, do this for you automatically. You can see exactly what is sent using</p>
<div class="language-bash codeBlockContainer_OZUn theme-code-block" style=--prism-color:#393A34;--prism-background-color:#f6f8fa><div class=codeBlockContent_Prpx><pre tabindex=0 class="prism-code language-bash codeBlock_mFd_ thin-scrollbar" style=color:#393A34;background-color:#f6f8fa><code class=codeBlockLines_aUJ3><span class=token-line style=color:#393A34><span class="token plain">curl -vv</span><br/></span></code></pre></div></div>
<p>in the example above.</p>
<p><strong>Do not use a GET request to call /siteverify.</strong> Use a POST request, and pass the parameters in the form body, not the URL.</p>
<p>While the endpoint may respond correctly to a GET request or to a POST request that uses URL parameters, this is not guaranteed. If the parameters you send to GET are too long, the request will fail and you will be unable to validate passcodes. Using a POST request ensures you will not have this problem.</p>
<p>Please note that you must call <code>/siteverify</code> with your account secret in order to validate passcodes users send you are real and unexpired. You will also be unable to validate passcodes from a sitekey in one account if using a different account's secret.</p>

<p>These are the error codes that can be returned by the hCaptcha API:</p>
<table><thead><tr><th>Error Code<th>Description<tbody><tr><td>missing-input-secret<td>Your secret key is missing.<tr><td>invalid-input-secret<td>Your secret key is invalid or malformed.<tr><td>missing-input-response<td>The response parameter (verification token) is missing.<tr><td>invalid-input-response<td>The response parameter (verification token) is invalid or malformed.<tr><td>expired-input-response<td>The response parameter (verification token) is expired. (120s default)<tr><td>already-seen-response<td>The response parameter (verification token) was already verified once.<tr><td>bad-request<td>The request is invalid or malformed.<tr><td>missing-remoteip<td>The remoteip parameter is missing.<tr><td>invalid-remoteip<td>The remoteip parameter is not a valid IP address or blinded value.<tr><td>not-using-dummy-passcode<td>You have used a testing sitekey but have not used its matching secret.<tr><td>sitekey-secret-mismatch<td>The sitekey is not registered with the provided secret.</table>
<h3 class="anchor anchorTargetStickyNavbar_i37j" id=rotating-your-siteverify-secret>Rotating Your Siteverify Secret<a href=#rotating-your-siteverify-secret class=hash-link aria-label="Direct link to Rotating Your Siteverify Secret" title="Direct link to Rotating Your Siteverify Secret" translate=no>​</a></h3>
<p>Your siteverify secret is solely for secure machine-to-machine authentication; it should never be exposed publicly.</p>
<p>If your siteverify secret has been unintentionally exposed, you may receive an email warning from us.</p>
<p>You can also rotate it yourself at any time by visiting the Dashboard, choosing your profile icon and Settings menu option, and then clicking <code>Generate New Secret</code>. <strong>Make sure to copy that value!</strong> We don't retain it, so you won't be able to see it again.</p>
<p>You will receive an email confirmation within a few seconds of rotation.</p>
<p><strong>Note:</strong> Free users may rotate the secret once per day. Pro users may rotate secrets up to 3 times per day. Enterprise users have additional options to manage secrets.</p>
<p>For example, Enterprise accounts can create multiple Sitekey Secrets with an optional expiry and assign secrets to one or many sitekeys to enable segmentation of secrets by environment, unique keys per team, and more. Please see the Enterprise docs for more details.</p>
<h2 class="anchor anchorTargetStickyNavbar_i37j" id=local-development>Local Development<a href=#local-development class=hash-link aria-label="Direct link to Local Development" title="Direct link to Local Development" translate=no>​</a></h2>
<p>If you are developing on your local machine there are a few things to keep in mind.</p>
<p>Modern browsers have strict CORS and CORB rules, so opening a <code>file://URI</code> that loads hCaptcha will not work. Loading hCaptcha from <code>http://localhost/</code> will encounter the same issue on some browsers. The hCaptcha API also prohibits <code>localhost</code> and <code>127.0.0.1</code> as supplied hostnames.</p>
<p>The simplest way to circumvent these issues is to add a hosts entry. For example:</p>
<div class="language-text codeBlockContainer_OZUn theme-code-block" style=--prism-color:#393A34;--prism-background-color:#f6f8fa><div class=codeBlockContent_Prpx><pre tabindex=0 class="prism-code language-text codeBlock_mFd_ thin-scrollbar" style=color:#393A34;background-color:#f6f8fa><code class=codeBlockLines_aUJ3><span class=token-line style=color:#393A34><span class="token plain">127.0.0.1 test.mydomain.com</span><br/></span></code></pre></div></div>
<p>Place this in <code>/etc/hosts</code> on Linux, <code>/private/etc/hosts</code> on Mac OS X, or <code>C:\Windows\System32\Drivers\etc\hosts</code> on Windows.</p>
<p>You can then access your local server via <a href=http://test.mydomain.com target=_blank rel="noopener noreferrer" class="">http://test.mydomain.com</a>, and everything will work as expected.</p>

<h3 class="anchor anchorTargetStickyNavbar_i37j" id=frontend-testing-force-a-visual-challenge>Frontend Testing: Force a Visual Challenge<a href=#frontend-testing-force-a-visual-challenge class=hash-link aria-label="Direct link to Frontend Testing: Force a Visual Challenge" title="Direct link to Frontend Testing: Force a Visual Challenge" translate=no>​</a></h3>

<p>If you are an Enterprise customer, just add a "Challenge" rule targeting your IP or user agent.</p>
<p>If you are using the Pro or free service, one option is to add a second sitekey set to "Always Challenge" mode. Note that "challenge" does not automatically mean "visual challenge" in our system, but if you rapidly reload several times you are likely to start seeing visual challenges.</p>

<p>If the token the user sends to you is invalid or expired, the <code>siteverify</code> response will contain <code>success: false</code>. This means you can safely block the request.</p>
<p>To test this, simply use a nonsense string like "FAKE-TOKEN" in your backend integration tests when you want to validate end-to-end failure behavior.</p>
