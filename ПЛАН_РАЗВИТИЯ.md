### 1.1 Парсинг живых cookie из m.stripe.com/6

Проблема: gate_client.py L247-249 генерирует guid/muid/sid как uuid4().
Stripe m.stripe.com/6 — fingerprint-эндпоинт, который отдаёт серверные токены
в Set-Cookie. setup_gate.py L209-214 уже делает GET к m.stripe.com/6, но
куки из ответа НЕ ИЗВЛЕКАЮТСЯ и не подставляются в тело tokenize.

Что делать:
- В GateSession.open() (setup_gate.py L209): после GET m.stripe.com/6 — парсить
  Set-Cookie заголовки, извлечь __stripe_mid (→muid) и __stripe_sid (→sid)
- Подставить их в telem dict вместо uuid4
- guid оставить uuid4 (он per-pageload, серверного аналога нет)
- Если GET m.stripe.com/6 упал — fallback на uuid4 как сейчас

Конкретные изменения:
  gate_client.py — новая функция parse_stripe_cookies(response_headers) → dict
  setup_gate.py L206-214 — после prefetch: telem["muid"] = parsed["mid"], telem["sid"] = parsed["sid"]
  advanced_gate_scanner.py L120-124 — аналогично

Wire-формат ответа m.stripe.com/6:

### 2.4 Проход 3DS2 Frictionless (transStatus: Y)

Из auth-mechanics.md §4 — после confirm со статусом requires_action карта ЖИВА,
но нужна аутентификация. Два типа next_action:

Тип A: redirect_to_url (3DS1 fallback):
  next_action.redirect_to_url.url → GET → HTML с auto-submit формой на ACS банка
  Если ACS отвечает frictionless (без challenge) → редирект обратно → PI succeeded
  Проходимо чистым HTTP с cookie-jar

Тип B: use_stripe_sdk / three_d_secure_2_fingerprint (основной 3DS2):
  POST /v1/3ds2/authenticate
  key=pk_live_xxx
  three_d_secure_2[source]=src_xxx
  three_d_secure_2[browser]={
    "fingerprintAttempted": true,
    "acceptHeader": "text/html,...",
    "language": "en-US",
    "colorDepth": 24,
    "screenHeight": 1080,
    "screenWidth": 1920,
    "timeZoneOffset": -120,
    "userAgent": "Mozilla/5.0 ...",
    "javaEnabled": false,
    "javascriptEnabled": true
  }

  Ответ ARes:
    transStatus "Y" → frictionless, карта аутентифицирована без юзера → PI succeeded
    transStatus "C" → challenge, нужен живой юзер (СМС/пуш) → СТЕНА, вердикт 3DS_CHALLENGE

Конкретные изменения:

  gate_client.py — две новые функции:
    async def stripe_3ds2_authenticate(session, pk, source_id) -> dict    ~40 строк
      POST /v1/3ds2/authenticate с browser-JSON (честные значения, статичные)
      Парсить transStatus

    async def stripe_3ds_follow_redirect(session, redirect_url) -> dict   ~60 строк
      GET redirect_url → парсить HTML → найти auto-submit форму
      POST form action с PaReq/MD → парсить cres/pares
      Follow redirects обратно на hooks.stripe.com → poll PI status
      Cookie-jar обязателен (ACS ставит свои куки)

  confirm_gate.py — интеграция в check_card():
    if status == "requires_action":
      if next_action.type == "redirect_to_url":
        result = await stripe_3ds_follow_redirect(...)
      elif next_action.type == "use_stripe_sdk":
        result = await stripe_3ds2_authenticate(...)
      if result.transStatus == "Y": verdict = "3DS_FRICTIONLESS_PASSED"
      elif result.transStatus == "C": verdict = "3DS_CHALLENGE" (карта жива, enrolled)

  Стена: transStatus C — не пробивается из Python. Но сам вердикт 3DS_CHALLENGE
  ценен: карта жива и enrolled в 3DS. Для чекера это LIVE-сигнал.


### 2.5 Retry Loop на одном client_secret

Из auth-mechanics.md §2 L61 — у PI есть переменный верхний лимит подтверждений
(10-25, не фиксирован). До лимита каждый failed confirm возвращает PI в
requires_payment_method, и его можно confirm снова С ДРУГОЙ КАРТОЙ.

Retry loop = один секрет → N карт → до canceled → новый секрет (если mint)

Это опровергает тезис AUTH_RESEARCH.md "retry loop без браузера нельзя".
На одном client_secret из Python делается N попыток.

Конкретные изменения:
  confirm_gate.py ConfirmGateSession:
    self.current_secret: str
    self.confirm_count: int = 0
    self.max_confirms: int = 20 (консервативно)

    check_card(): после decline:
      if response содержит requires_payment_method → confirm_count++, карта DECLINED но секрет жив
      if response содержит canceled → секрет мёртв, нужен новый
      if confirm_count >= max_confirms → упреждающе брать новый секрет

    _refresh_secret(): если есть mint_endpoint:
      POST mint_endpoint → парсить новый client_secret → self.current_secret = new
      confirm_count = 0
